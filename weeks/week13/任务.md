# W13 每周任务：真实仓库中的第一次安全改动

- **日期**：2027-02-01 ～ 2027-02-07
- **截止**：2027-02-07（周日）23:59，中国标准时间 UTC+8
- **投入预算**：7 小时/人；阅读 2h／修改 2h／验证 2h／PR 1h
- **完成形式**：四人各自独立完成；允许查文档和使用 AI，但必须能解释自己的代码。
- **先读**：[知识.md](知识.md)；W02 另有专题知识文档。

## 本周要达成什么能力？

完成一次低风险、可回滚、可证明的实际修改。

## 完成路径（按顺序做）

1. 从主力维护的“安全小任务列表”选 1 项，先复述预期行为。
2. 新建分支修改，并给出修改前后对比。
3. 用已有离线视频或测试命令验证正常与异常路径。
4. 提交 PR，修复审查意见并完成复盘。

## 基础必做（以可复现为准）

- [ ] 一个小范围 PR
- [ ] 修改动机及影响范围
- [ ] 至少一组回归测试
- [ ] 简短复盘

## 选做挑战（不作为留队硬门槛）

- 为旧 bug 添加最小复现脚本

## 交付方式与证据

1. 在本人分支或个人提交目录中上传源码、CMakeLists、README 与测试记录；不要上传 `build/`、系统文件、未授权比赛视频、设备密钥。
2. 至少记录一次“错误现象 → 排查动作 → 最终结论”；即使未解决，也记录已验证的事实。
3. 提交一个 PR（初期不会 PR 可以先提交个人分支并报告链接），标题格式：`W13 学员昵称 - 任务主题`。
4. PR 描述复制 [提交模板](../../templates/SUBMISSION_TEMPLATE.md)，不得只上传截图而没有源码。

## 验收清单（主力抽查）

- [ ] PR 不包含无关大规模格式化
- [ ] 能够回滚
- [ ] 实际修改与测试记录对应

### 口头/录屏追问（任选 1～2 题）

1. 为什么小 PR 更容易 review？
2. 怎样证明你的修改没有破坏原本 3m 自瞄效果？（若无法实测，明确验证边界）

## 如果做不出来怎么办？

- 先完成能工作的最小版本，不要为了选做任务耗光 7 小时。
- 超过 30 分钟仍卡住，按 [求助模板](../../templates/HELP_TEMPLATE.md) 记录现象、尝试和日志，发 GitHub Issue / 群里求助。
- 截止前主动说明卡点可申请一次补交；**未完成但有真实排错记录**，与无说明不提交区别评价。
- 本周属于培训计划，不需要实车联调或新模型训练。
